# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Package manager

This repo uses **pnpm** (`pnpm-lock.yaml`), not npm or yarn. Running `npm install` against it will produce peer-dependency resolution errors — always use `pnpm`. A hook in `.claude/settings.json` blocks `npm` and `npx` commands.

Node and pnpm versions come from `mise.toml` (major only; `mise upgrade` takes the newest). To upgrade dependencies: `pnpm update --latest --include-github-actions`. It skips the pins in `pnpm-workspace.yaml`'s `updateConfig` (`nuxt`, `typescript`, `@vueuse/nuxt`; reasons there and in `docs/adr/0002-dependency-pins.md`), so don't override them by hand. `tailwindcss` is not a direct dependency: it comes with `@nuxt/ui`. A `@playwright/test` bump also needs the image tag in `package.json`'s `visual` script and `check.yml` (`visualImage.test.ts` fails otherwise) and `pnpm exec playwright install chromium`.

## Commands

```bash
pnpm dev              # dev server at http://localhost:3000
pnpm build            # production build
pnpm generate         # static generate (`pnpm wavedash:build` builds on it)
pnpm preview          # preview a static build locally

pnpm test             # vitest, all unit tests (app/tests/*.test.ts)
pnpm test app/tests/sudokuGrader.test.ts   # single unit test file
pnpm test:e2e         # Playwright e2e suite (e2e/*.spec.ts)
pnpm test:e2e e2e/pause.spec.ts             # single e2e file
pnpm test:prod        # Wavedash build + smoke test of it served from a subfolder (e2e/prod.spec.ts)

pnpm fmt              # oxfmt (also runs automatically on commit, see below)
pnpm lint             # oxlint (also runs automatically on commit, see below)
```

Don't run `fmt`/`lint` proactively during normal development — `forge.toml` wires `oxfmt` and `oxlint` into a pre-commit hook (auto-fixing and restaging), and `commit-msg` enforces Conventional Commits. They run automatically at commit time, **once the hooks are installed**: a fresh clone has none, so run `forge install` and then `git config core.hooksPath "$PWD/.forge/hooks"` (forge writes a relative path, and `.forge/` is gitignored, so worktrees under `.claude/worktrees/` would otherwise run no hooks). `forge run pre-commit --all-files --check` verifies. CI runs `pnpm check` (`.github/workflows/check.yml`) as the backstop.

The e2e suite spins up its own dev server on port 3110 (`E2E_PORT` overrides it, so separate checkouts can run at once) with `NUXT_IGNORE_LOCK=1` (see `playwright.config.ts`), so it can run even while a normal `pnpm dev` is active on another port — Nuxt's dev-server lock is keyed by project directory, not port, so this would otherwise fail with "Another Nuxt dev server is already running." Playwright tests run with `workers: 1`: a single dev-mode Nuxt server backing all tests causes contention/flakiness under parallel workers.

`vitest.config.ts` collects only `app/tests/**/*.test.ts`: the default glob also picks up the Playwright `.spec.ts` files, and the whole repos checked out under `.claude/worktrees/` (thousands of their dependencies' tests).

## Architecture

This is a client-only SPA (`ssr: false` in `nuxt.config.ts`), statically generated and shipped to Wavedash (`pnpm wavedash`). There is no `pages/` directory — `app/app.vue` is the entire app. It's a single root component that owns the game's state and flow (the board via `useSudokuEngine`, the clock and pause via `useGameSession`, input via `useGameInput`, the modals, wins and saves) and switches between screens itself via a `currentScreen` ref (`"menu" | "difficulty" | "game" | "academy" | "custom-import" | "stats"`), not Nuxt routing.

Imports: `.vue` files rely on Nuxt auto-imports (vue APIs, components, `composables/`, top-level `utils/` exports) and import only types and external packages; oxlint's `no-restricted-imports` enforces it. `.ts` files (utils, composables, plugins, tests) keep explicit imports, because vitest runs them without Nuxt.

### Two separate Sudoku solvers, for different jobs

- **`app/utils/sudokuCore.ts`** — array-based backtracking solver (`solveBoard`, `isValidPlacement`, `countSolutions`/`hasUniqueSolution`) used for puzzle generation and uniqueness checks. This is the "can this board be solved at all / does it have exactly one solution" layer.
- **`app/utils/sudokuGrader.ts`** — a separate bitmask-based solver that mimics _human_ solving techniques (naked/hidden singles through XYZ-wing, see `TechniqueId`). It never peeks at the answer key: every move it returns (`SolveMove`) is justified by the technique itself, either a forced `placement` or a list of candidate `eliminations`. This same engine powers three things at once:
  1. **Hints** — `nextHint()` returns the next logically-justified move, replayed by `useSudokuEngine`'s `triggerComplexHint`/`applyComplexHint`.
  2. **Difficulty grading** — `solveLogically`/`gradePuzzle` grade a puzzle 1–5 (or `STUCK` if no technique applies and brute force would be required).
  3. **Puzzle generation** — `generateGradedPuzzle` digs cells out of a solved grid (via `sudokuCore`) and keeps retrying until the result fits the target (`DIFFICULTY_TARGETS`): its tier within `[min, max]` and, from Hard up, its count of moves at tier 3+ within `hard` (Hard 1–2, Expert 3+ with nothing past tier 4, Master 5+ with a tier-5 move; the tier alone made all three "one hard move" boards), falling back to the closest _solved_ (never `STUCK`) board it saw. Generation never ships a guess-only puzzle.

### State composables

- **`useGameSession.ts`** — the game clock (`useTimer`) and what's around it: the pause, Settings over the paused game, the shortcuts sheet, the controls tour, pausing when the tab is hidden. The clock is never started or stopped directly: **`useClockHolds.ts`** keeps a set of hold reasons (`"paused"`, the player's, the only one with the pause overlay, also set by a hidden tab or a lesson opened from the game; `"tour"`, a first controls tour; `"finished"`, the end modal or Finish) and it runs iff the game screen is up and the set is empty. A new reason to stop the clock is a new hold, not a `stopTimer` call.
- **`useGameInput.ts`** — the numpad, cell taps and game keys: digit-first arming (`activeDigit`), the picked digit, `handleKeyDown`. What a digit does to the board stays in `app.vue` (`handleInputNumber`), passed in with the other actions.
- **`useSudokuEngine.ts`** — the board/notes/history/hint state machine. Takes `colorMode` (a `Ref<boolean>`) so hint text can route digits through `digitLabel()` and say "red" instead of "5" when color mode is on.
- **`useGameSave.ts`** — one save slot per difficulty (`sudoku_v1_save_<difficulty>`), via `safeJson.ts`. There's no global "continue" — picking a difficulty that already has a save triggers a resume-or-restart prompt (`pendingResume` in `app.vue`) instead.
- **`useDailyPuzzle.ts`** — date-seeded (`seedFromString` + `makeRng`) puzzle, same for everyone on a given local calendar day; tracks completion/streak.
- **`useScore.ts`**, **`useTechniqueStats.ts`** — lifetime score and per-technique usage stats, also via `safeJson.ts`.
- **`app/utils/safeJson.ts`** — the shared `readJSON`/`writeJSON`/`removeJSON` every persistence composable uses (SSR-safe, try/catch'd: a sandboxed iframe can throw on any storage access). Reach for this instead of hand-rolling another `localStorage` guard; oxlint's `no-restricted-globals` rejects `localStorage`/`sessionStorage` in `app/` outside the storage layer (allow-list in `.oxlintrc.json`).

### Gamification

Progress features are all derived from a win, with the rules in **pure, unit-tested utils** and persistence in thin composables (via `safeJson.ts`):

- **`utils/achievements.ts`** — the achievement rules: most are a `check(WinSummary)` on a won game (`triggerLocalModal` in `app.vue` builds the summary after `score.record`, calls `useAchievements().evaluate`, and queues the new ids as toasts); the Academy ones are an `academy(AcademySummary)` check, run by `academyCue` in `app.vue` after each lesson, Spot it or How to play move. Unlock timestamps live in `sudoku_v1_achievements`. Adding an achievement = a rule here + `achievements.<id>.name/desc` in both locales (a test enforces both).
- **`utils/level.ts`** — lifetime score → level (reaching level n costs 250·n·(n−1) points) and a title band. **`utils/stars.ts`** — 1–3 stars for the win modal. **`utils/mastery.ts`** — Familiar/Practised/Fluent tiers for the Academy badges. **`utils/calendar.ts`** — the 12-week Monday-first grid behind the stats `DailyCalendar`.
- **How to play** (`utils/basics.ts`, `components/BasicsLesson.vue`, the `basics` screen) — four hand-built beginner lessons (the rule, pencil marks, one mark left, scanning) before the technique path, shown as its step 0. Every board is cut from one solved grid (`SOLUTION`) and a test proves each asked answer is forced. Its own small engine (place a digit / pencil in the maybes), so wrong input gets the beginner's reason ("This row already has 4", "Row 2 already has 5, so this cell is ruled out"; never a sentence starting with the digit, which colour mode turns into a word). Done lessons in `sudoku_v1_basics_done`, union-merged by cloud sync (`mergedBests`); the menu offers the course to a player with no wins and no lessons until dismissed (`pref_basics_prompt`).
- **Guided lessons** (`utils/lesson.ts`, `components/TechniqueLesson.vue`, the `lesson` screen) — the solver replayed over a practice puzzle to where the technique is next (else the Academy example): find the pattern cells, then make exactly its placement or removals. Its own board state, no clock/score/save. Finishing the next one is the only thing that completes a technique-path challenge (`completesChallenge`); a full practice win is extra practice, and only marks the technique of the week. A wrong tap gets the first true reason `missReason` finds; a fish accepts any same-size twin on its digit (`instancesOf`); the Academy-example fallback is shuffled by a sudoku symmetry (`shuffleLesson`) so "Another example" never repeats. Show me and rejected moves cost stars (`starsFor`); a finished lesson also lifts the Academy mastery badge (`masteryFor`).
  - **Three levels** per lesson, the table in `guideOf`: 1 names and marks where to look (`guideUnits`, the board's `nudge`), on rows; 2 the same on columns for a pattern built along lines, else less help (the unit named, or just the digit); 3 "On your own", nothing named. `turnFor` transposes the position (`shuffleLesson`'s `turn`) so narration and reasons say columns. At level 3 any real instance on the board counts (`instancesOf(L, 3)`, each carrying its own `move`, which step 2 uses) and a wrong tap's reason never names the digit or unit. Stars per level: level 1 in `sudoku_v1_lesson_stars` (as before levels), 2 and 3 in `sudoku_v1_lesson_stars_2`/`_3` (`LESSON_STARS_KEYS`), each max-merged by cloud sync (`mergedBests`). Finishing a level opens the next; the Academy and the path open the first unfinished, a technique a game or drill showed was missed opens at level 1. Done: Enter (A) is the next level, the D-pad walks the buttons; L (LT) changes level. e2e pins a position with `window.lessonSeed`.
- **Spot it** (`utils/spotIt.ts`, `components/SpotIt.vue`, the `spot` screen) — a timed round of ten lesson step-1s from one tier (`buildRound`, seeded per position), sharing the lesson's `tapPattern`/`missText`/`findPrompt`. Positions come from `quickLesson` in the puzzle worker (`makeLesson` in `puzzlePool.ts`), one ahead; rare techniques skip the search and use the shuffled example. Best time per tier in `sudoku_v1_spot_best`, min-merged by cloud sync. e2e pins a round with `window.spotSeed`.
- **Daily review** (`utils/review.ts`, `components/ReviewPanel.vue`; plays in `SpotIt.vue` with its `review` prop: no clock or penalties) — a Leitner schedule over the techniques whose lessons were finished: box 1 due tomorrow after a lesson, a pass (≤ 1 wrong tap, no skip) moves up a box (1/3/7/14/30 days), a miss back to box 1. Cards in `sudoku_v1_review` ({id: {box, next}}, local date keys); lessons finished before it existed join as due today (`withLearned`, nothing stored). Cloud sync keeps each technique's card set last: its due date less its interval, a same-day miss winning (`mergeReview`). **Own positions**: a hint past the singles (tier ≥ 2, peeks too) in a scored, Zen or custom game, classic only (lessons and Spot it have no X-Sudoku), stores the position before it was applied (`stuckAt` in `app.vue`: right digits and the chain's `appliedEliminations`, as `stuckPosition`) in `sudoku_v1_review_positions` ({id: {board, elims, date}}, newest per technique) and gives the technique a card if it has none (`rememberStuck`; a hint never resets one). That card's next review plays it ("From your game on …") via the worker's `lessonFrom` job, `lessonFromPosition` (which rejects an unsound position: it's then dropped for a generated one), and consumes it once played. Cloud sync keeps the newer per technique (`mergePositions`).
- **`utils/records.ts`** — personal records (`sudoku_v1_records`, via `useRecords`): most wins in a day, longest clean run, hardest level won without hints, counted from scored and Zen wins (never practice or custom boards, which could be farmed; the first mistake in a game ends the clean run). Fastest times stay in `useScore` and the longest Daily streak is derived from the Daily history, not stored. `triggerLocalModal` snapshots before/after a win and `brokenRecords` gives the win-modal lines; a cloud sync max-merges the bests both ways (`mergedRecords`).
- The win modal plays in steps (`winStep`: stars, score lines, the "Perfect!" stamp); unrevealed parts are only `opacity-0`, so the DOM always holds the real numbers. A tap or key skips; reduced motion starts at the end. A win turns the page to it (`.page-turn`). After the steps, "What you needed help with" (`hintRecap` in `utils/winRecap.ts`) lists up to three techniques the game's hints applied, hardest first, each opening its lesson at the first unfinished level (Back lands on the Academy); the counts (`hinted`) live in the game's save, and practice boards show none.
- **Watch your solve** (`SolveReplay.vue`, `utils/replay.ts`) plays on the game's own board: it emits frames, the win modal goes `invisible`, and `app.vue` swaps in a read-only grid. Gold marks are the moves past the singles (`hardMoves`, via `techniqueFor`). **See it in 3D** opens `SolveSkyline.vue` (`utils/skyline.ts`), the only code that loads three.js: a dynamic import on mount, its own lazy chunk (the budget's `FAIL_AT` was raised for it). Keep three out of anything eager.
- **You spotted it**: taking out the last pencil mark of a technique's removals (`spottedMove`, on the board the notes show via `notesEliminations`) names it over the board and draws it in pen, once per technique per game. The idle hint panel lists what applies right now (`availableTechniques`, notes counted); a name the solver's own candidates also give (`peekMoves` in the engine: never the notes, which may be a guess, and never the answer key, which would tell which guesses are right) is a button that opens it as a hint starting a step earlier, on where to look (`peekMove`, `lookUnit`: the unit framed, no target or pattern yet), free to look at and a hint once applied. On that step a board tap (or Enter/Space on the selected cell) marks a guess at the pattern instead of selecting (`tapPeek`; the cells are `patternCells` in `sudokuGrader.ts`, the same a lesson's step 1 asks for): all of them found moves on to the pattern step, and with no miss and no Next first, applying it charges no hint (`peekFree`; `techStats` still records it). A miss gets a reason only from checks that name nothing new (filled, outside the named unit, a naked single's cell with more candidates), never `lesson.ts`, which is lazy-only. Below lg the idle panel is only that list, one sideways-scrolling row under the numpad (where an open hint shows on phones), hidden while empty, during a nudge or the pause.
- **Can this go?** (`CanThisGo.vue`, under the hint panel; under the numpad on phones): with a noted empty cell selected, each pencil mark is a button asking whether anything rules it out: a digit its units hold, else `removerOf(engine.peekMoves(), mark)`, whose Show me opens that move as a peek (a hint once applied). Never the answer key: "nothing yet" says nothing about whether the mark is right.
- **This board hides: X**: a game names the hardest technique its board needs (`featuredTechnique` in `sudokuGrader.ts`: `neededTechniques`' first, null for singles-only or `STUCK` boards), on the board's top edge (absolute, so it never moves the board) until the first move or ✕, and in the pause overlay; tapping opens its lesson (`openGameLesson`). Board metadata like the level, not a hint. The worker works it out: new games and Dailies carry it in their job result (`technique`, read off the finished board, so seeded boards don't change), a save stores it, and an older save or a custom board asks `featuredOf` (a worker job, so it can queue behind a prefetch). Hidden in practice games and when `announceTechnique` (Settings, by the hint style) is off. When "You spotted it" fires for it, it says "You found the board's X" (`spottedMove`'s limits: removal moves only, each finder's first instance).
- Hidden achievements are masked as `???` in the trophy case until unlocked.
- **Wavedash** (`utils/wavedash.ts`, the only code touching the injected SDK; a no-op elsewhere) mirrors unlocks to Wavedash achievements. `wavedash-achievements.json` is the portal import file, generated from the rules: after changing an achievement or a stat (`STAT_NAMES` in `utils/wavedash.ts`, values from `readPlayerStats`; they only grow, so a lower local value is never sent) run `UPDATE_WAVEDASH=1 pnpm test wavedash` and re-import it. Wins also post to leaderboards (`scoresFor`/`submitWin`; never custom puzzles), shown by `LeaderboardPanel` in Stats only on Wavedash; Progress syncs to one cloud file (`progress.json`, a Settings export): the async plugin restores or uploads before the app mounts (`decide` in `utils/cloudSync.ts`), and wins and hiding the tab upload. e2e fakes the SDK with `e2e/fakeWavedash.ts`. Design: `docs/specs/2026-10-27-wavedash-platform-design.md`.

### Preferences, feedback and backup

- **`composables/usePreferences.ts`** is the single owner of every player setting (`sudoku_v1_pref_*`; module-level singleton refs shared by the game and Settings). Add a setting there, then read it where needed.
- **`cue(kind)` in `app.vue`** is how game events produce feedback: it plays the sound (`utils/sound.ts`, synthesized) and the vibration (`utils/haptics.ts`), each behind its own preference. Use it rather than calling `playX` directly.
- **Digit-first input** (`activeDigit` in `useGameInput`) arms a digit from the numpad; `handleSelectCell` places it, but arrow keys set `selectedCell` directly so they never place.
- **Turning the board** (the dashboard's turn button, R, RT): `engine.turn` counts clockwise quarter turns (back to 0 on every new board), display only, so saves, scores and `data-cell` stay in data coordinates. `SudokuGrid` turns as one transform (its `PatternOverlay` with it) and each cell's contents turn back (static per turn: no per-move transition). Everything that names or walks a position goes through `utils/boardTurn.ts` (data (r, c) shows at (c, 8 − r)): hint text narrates `turnMove` and is retold on a turn, the nudge, the mistake explainer, cell aria-labels, arrows (`stepCell`'s `turn`), the pen's pencil-mark slots (`turnSlot`) and the win wave. The replay follows the turn; lessons, drills and the skyline don't turn.
- **Completion flashes** carry a per-cell `delay` (`FlashCell`): a ripple from the placed digit, and a diagonal wave on a win (the win modal fades in after it via `.modal-delay`).
- **Menu paper**: a puzzle page drifts behind the menu (`.menu-drift` in `MainMenu.vue`; the board grain on Newsprint/Chalkboard is in `SudokuGrid.vue`). It follows the season (`seasonFor` in `utils/season.ts`, local month): a few pen-drawn snowflakes and ink dots Dec–Feb, petals Mar–May, leaves Sep–Nov, plain paper in summer. Menu only, at most nine `.season-bit`s animating transform/opacity, hidden under reduced motion. `window.season` pins it; `visual.spec.ts` pins `summer` so baselines don't follow the calendar.
- **`utils/progressBackup.ts`** exports/imports every `sudoku_v1_*` key as a JSON file (Settings → Your data). It validates strictly (right app/version, our prefix only, JSON values, size cap) and import _replaces_ then reloads. New storage keys must keep the `sudoku_v1_` prefix to be backed up.
- Component styles that need a dark variant must use Tailwind `dark:` classes or a **non-scoped** `.dark .x` rule: scoped `:global(.dark) .x` silently failed (axe caught it).

### Color mode

`app/utils/sudokuColors.ts` defines `SUDOKU_COLORS` (digit 1–9 → Tailwind color class), `dotClass(n)` (colour + a circle/square/diamond shape cue for colour-blind players) and `digitLabel(n, colorMode, t)`, which both the UI (`SudokuCell`, `Numpad`, `DifficultySelector`) and the hint engine use so a digit is rendered/described consistently as a color when the mode is on. The underlying board state is always numeric — color mode is a rendering/copy concern only, toggled before a game starts and locked for its duration.

### Academy examples are generated data

`app/utils/academyExamples.ts` is auto-generated (per its own header comment) from real harvested solver states — one genuine example board per technique, not hand-written. Don't hand-edit it.

Patterns are drawn in pen over the board, the way puzzle books print them: `utils/patternMarks.ts` turns a `SolveMove` into lines (strong links solid, weak links and cover lines dashed) joining the actual pencil-mark slots, rings, unit frames, red-pen crosses and placement circles; `PatternOverlay.vue` is one SVG over the board (`SudokuGrid`'s `marks` prop, or `ExampleGrid`). Lessons, in-game hints and the Academy examples all use it. A new technique needs a case in `patternMarks` (its test draws every Academy example). The Academy cards' **Watch it** (`WatchExample.vue`) plays that drawing in steps (`beats`: frames, rings, links, result). The Academy's **map** view lays the techniques out by tier (`MAP_COLUMN`) with a line for each `BUILDS_ON` link in `utils/progression.ts`; a new technique needs both.

### i18n

Two locales: `en` and `rs` (`code: "rs"`, not `"sr"` — renamed from `sr` because i18n-ally was resolving the bare language code to the Suriname flag instead of Serbia's; `language: "sr-Latn-RS"`, the actual BCP-47 tag, is unaffected). Locale files use **flat dot-keys** (e.g. `"menu.title"`, not nested `{ "menu": { "title" } }`) per `.vscode/settings.json`'s `i18n-ally.keystyle: "flat"`. This works because vue-i18n checks for an exact literal-string key match before falling back to nested path resolution — it is not a bug. Keep `en.json` and `rs.json` in exact key parity: `app/tests/localeParity.test.ts` checks the keys, each key's `{placeholders}` and that no value is empty.

### Visual regression

`e2e/visual.spec.ts` captures every screen in light + dark against pixel baselines in `e2e/visual-regression-snapshots/<project>/`, at 1920×1080 (`visual`) and Pixel 7 (`visual-mobile`). It is opt-in (`VISUAL_REGRESSION=1`, so plain `pnpm test:e2e` skips it) and seeds a fixed saved game so nothing is random.

```bash
pnpm visual          # compare against baselines (in Docker)
pnpm visual:update   # accept intentional UI changes, then commit the PNGs
pnpm visual:run      # the bare Playwright run, used inside the container
```

Baselines are Linux renders from the official Playwright image (`mcr.microsoft.com/playwright`, tag = the installed `@playwright/test`; `app/tests/visualImage.test.ts` fails if they drift). `pnpm visual` runs the suite in that image via `scripts/visual-docker.sh` (Docker required; always `linux/amd64`, emulated and slower on an Apple Silicon Mac, because arm64 rasterizes differently from CI; `.nuxt` and `.data` stay in the container; node_modules is a volume per checkout). `pnpm test:all` ends with `pnpm visual`, so it needs Docker too. CI doesn't run it (no runner minutes to spare): it's a local check, before a release or when a UI change wants a look. `pnpm visual:update -g <name>` re-renders only the matching screens. Never run `pnpm visual:run` on the host to update baselines: host font rendering differs. Baselines go stale between runs; whoever runs it next updates the ones a deliberate change moved. Never reuse a running dev server for these runs (the config forbids it): Nuxt DevTools is disabled only for fresh servers.

### Performance

Laptops with integrated graphics (an i7 + Iris Xe) are the low end. Measure before changing anything, against a production build (`pnpm wavedash:build`, served from a subfolder by `scripts/serve-static.mjs`), never the dev server, with Playwright's Chromium at 1536×864 @1.25 and CDP `Emulation.setCPUThrottlingRate` 4 (a slow laptop). Play a real game: select cells, place digits, notes, undo, a hint, a win. CDP `Performance.getMetrics` splits main-thread time into script, style and layout.

- Moves cost style and paint, not script (3% of a move's CPU). A transition on the 81 cells restyled and repainted the board for every frame of a highlight change (45% of a move); `e2e/perf.spec.ts` checks that a move starts none. Animate one element, not every cell.
- Every generator runs in a Web Worker (`utils/puzzlePool.ts` + `puzzleWorker.ts`): new games (the difficulty screen prefetches one board per level, so starting one doesn't wait), the Dailies (the picked tile shows busy), practice puzzles and lessons. Without workers it generates in place. Both paths run `runPuzzleJob` (`utils/puzzleJobs.ts`), so a seed gives the same board either way (`puzzlePool.test.ts` checks the worker's own handler); jobs take a seed, never an rng. `countFlat` in `sudokuCore.ts` is the hot loop (typed arrays, most-constrained cell first); digging a cell asks for a second solution with that cell's digit banned instead of counting to two. A generator change must keep every seeded board: the daily pin in `dailyPuzzle.test.ts` fails otherwise. A solver/grader change (e.g. a new technique) changes the Dailies from its release on (Medium's rarely: it never needs past tier 2); dailyPuzzle.test.ts pins them so it's deliberate — release such changes and the Daily leaderboards split only for the day of release.
- `pnpm wavedash:build` (generate, then `scripts/budget.mjs`; `pnpm wavedash`, `test:prod` and the release all run it) first fails when `index.html`/`200.html` aren't the app shell (1.10.0 shipped "Redirecting..." pages and never loaded), then prints the shipped JS and CSS sizes and warns past `WARN_AT`. Locally size never fails the build (Wavedash's only limit is 1 GB per upload, docs.wavedash.com/publishing/upload); CI (`check.yml`) sets `BUDGET_STRICT=1`, which fails past `FAIL_AT` (raise it on purpose, with a reason, not to make a PR pass). Nuxt UI is the usual culprit: `import * as` from `@nuxt/ui/locale` bundled 67 locales (228 KB), and without `ui.experimental.componentDetection` it themes every component (120 KB of CSS). Find what grew with source maps (`sourcemap: { client: true }`) and `pnpm dlx source-map-explorer`.
- Only the menu, difficulty picker and game screen are in the entry chunk. The other screens and the end modal are `Lazy*` components in `app.vue`, and `academyExamples` ships only in the Academy chunk and the worker. Keep an eager component from importing lazy-only code: `useNudge` importing one helper from `lesson.ts` once pulled lesson, practice and the examples into the entry. Settings over the game loads its chunk before the sheet opens (`showModal()` focuses its first button).
- A lazy chunk that fails to load reloads the page (`plugins/chunk-reload.client.ts`, `experimental.emitRouteChunkError: "manual"`): Nuxt's own handler only reloads on a route change, and the app has none. `pnpm test:prod` 404s a chunk to check it, and checks the address stays `/game/` across a reload and a backup import. A win is recorded before its modal loads, so a reload loses nothing.

### Testing split

- `app/tests/*.test.ts` (vitest) — pure logic: solver, grader, scoring, daily-puzzle seeding. No DOM.
- `e2e/*.spec.ts` (Playwright Test) — full browser flows: new game/win, the resume-prompt's three branches, preference persistence, the pause overlay. Costs nothing to re-run once written, unlike manual browser-driven verification. Shared helpers (`BOARD`, `SOLVED`, `blank`, `grid`, `savedGame`, `playCustom`, …) live in `e2e/seed.ts`.
- Which to run: the unit file and the e2e specs that cover what changed (grep `e2e/` for the component or testid). The full e2e suite takes ~7 minutes: run it once before a release (it's the only place separately-tested PRs meet), not after every change. CI runs `pnpm check` on every PR.
- e2e runs against the dev server, so it can't catch a broken production build. `pnpm test:prod` does: it builds for Wavedash, serves `.output/public` under `/game/` (`scripts/serve-static.mjs`, the way Wavedash serves it) and runs `e2e/prod.spec.ts` (`playwright.prod.config.ts`; plain `pnpm test:e2e` skips it): it loads with no page or console error, starts an Easy game, opens an Academy card and Stats. CI runs it on every PR (`check.yml`) and the release runs it before upload. For anything else build-specific, extend that spec.

### Releasing

`pnpm wavedash:release --summary "…" --added "…" --fixed "…"` builds, uploads and publishes, titled with `package.json`'s version (bump it in a PR first). It has no `--help`: any run is a real release. It builds once (`pnpm wavedash:build`, which fails when `index.html`/`200.html` aren't the app shell: 1.10.0 shipped "Redirecting..." pages and never loaded), runs the prod smoke test on that build, and only then pushes (`scripts/release.mjs`); `pnpm wavedash` is the same build and push without the smoke test or publish. The build keeps the base URL at `/` and sets `NUXT_APP_CDN_URL=./` for relative asset URLs: a `./` base made Nuxt prerender those "Redirecting..." pages (4.6.3+) and rewrite the address from `/game/` to `/game/game/` on start, so any reload loaded a blank page (`docs/adr/0002-dependency-pins.md`). To roll back, there's no build list in the CLI: check out the last good release commit in a worktree, `pnpm install --frozen-lockfile`, `WAVEDASH=1 NUXT_APP_CDN_URL=./ pnpm exec nuxt generate`, then `wavedash build push` and `wavedash publish <build id> --title vX.Y.Z -y` (retry while it says "Only completed builds").
